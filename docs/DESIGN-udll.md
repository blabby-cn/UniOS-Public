# UniOS UDLL (Universal Dynamic Link Library) Design

## Overview

UDLL is UniOS's kernel-space dynamic shared library mechanism. It allows common functionality to be compiled once, placed on the FAT32 root filesystem, and loaded on demand by the kernel or by other kernel modules. The first UDLL is the shared file dialog (`/lib/filedlg.udll`) used by the built-in Notepad and any future application that needs to open or save files.

UDLLs are intentionally kernel-space libraries. UniOS is a monolithic kernel; kernel windows, the VFS, and the UI widget toolkit live in ring 0, so a reusable dialog must run in ring 0 to call `wm_*`, `ui_*`, and `vfs_*` directly.

## File Format

A `.udll` file is a custom binary format. It is not a raw ELF; it is a position-independent image produced from an ELF64 `.o` by `tools/udll_pack.py`.

    +------------------+
    | udll_hdr         | 64 bytes
    +------------------+
    | reloc table      | hdr.n_reloc * sizeof(udll_reloc)
    +------------------+
    | fixup table      | hdr.n_fixup * sizeof(udll_fixup)
    +------------------+
    | export table     | hdr.n_export * sizeof(udll_export)
    +------------------+
    | .text section    | hdr.text_size bytes
    +------------------+
    | .data section    | hdr.data_size bytes
    +------------------+
    | .bss section     | zero-filled, hdr.bss_size bytes
    +------------------+

### Header

```c
#define UDLL_MAGIC   0x55444C4C  /* "UDLL" */
#define UDLL_VERSION 1

struct udll_hdr
{
    uint32_t magic;
    uint32_t version;
    uint32_t text_size;
    uint32_t data_size;
    uint32_t bss_size;
    uint32_t n_reloc;
    uint32_t n_fixup;
    uint32_t n_export;
};
```

### Relocation Entry

Internal absolute references that need to be patched at load time:

```c
struct udll_reloc
{
    uint64_t offset;   /* offset inside the loaded image */
    uint32_t type;     /* relocation type */
    int64_t  addend;
};
```

Supported types:

- `UDLL_RELOC_ADDR64` — write `image_base + S + A` as a 64-bit value.
- `UDLL_RELOC_ADDR32` — write low 32 bits of `image_base + S + A`.

`S` is the symbol value (section base + symbol offset) and `A` is the addend from the ELF RELA record. These are pre-computed by `udll_pack.py` so the loader only adds the runtime base address.

### Fixup Entry

External symbol references. Each fixup names a kernel symbol that the loader resolves from the kernel symbol table.

```c
struct udll_fixup
{
    uint64_t offset;
    uint32_t type;
    int64_t  addend;
    char     name[32];
};
```

Supported types:

- `UDLL_FIXUP_ADDR64` — write the resolved kernel symbol address as 64 bits.
- `UDLL_FIXUP_ADDR32` — write low 32 bits of the resolved address.
- `UDLL_FIXUP_CALL32` — write a PC-relative 32-bit displacement to a 16-byte trampoline (`mov rax, addr; jmp rax`). The trampoline is generated by the loader so the UDLL can call any kernel function regardless of distance.

In practice, building with `clang -mcmodel=large` generates `ADDR64` fixups for external calls, so trampolines are rarely used.

### Export Entry

```c
struct udll_export
{
    char     name[32];
    uint64_t offset;
};
```

`udll_get_proc(handle, name)` returns `image_base + export.offset`.

## Building a UDLL

1. Compile a C source file with the kernel/U-space UDLL flags:

```bash
clang --target=x86_64-unknown-none-elf -ffreestanding -fno-stack-protector \
    -fno-builtin -nostdlib -mno-red-zone -mcmodel=large -O2 \
    -I src/kernel -c src/udll/filedlg/filedlg.c -o build/filedlg.o
```

2. Run the packer:

```bash
python tools/udll_pack.py build/filedlg.o build/filedlg.udll
```

3. Place the `.udll` on the FAT32 disk image. `tools/mkdisk.py` writes `build/filedlg.udll` to `/lib/filedlg.udll`.

### UDLL Coding Rules

- Include only kernel headers from `src/kernel/`.
- Do not use any C standard library functions except those exported in the kernel symbol table (`kmalloc`, `kfree`, `memset`, `memcpy`, `strcmp`, `strlen`, `strncmp`, `strncpy`, `strstr`, `kprintf`, `sched_ticks`).
- Do not use floating-point or SSE.
- Avoid global constructors and non-constant global initializers; `.bss` is zero-filled by the loader and `.data` is copied from the file, but complex constructors are not run.
- All cross-module calls must go through exported kernel functions.

## Kernel Loader

`src/kernel/udll.c` implements the loader:

```c
struct UdllHandle *udll_load(const char *path);
void *udll_get_proc(struct UdllHandle *h, const char *name);
void udll_unload(struct UdllHandle *h);
```

Load sequence:

1. Read the 64-byte header from VFS.
2. Validate magic and version.
3. Allocate one contiguous `kmalloc` block large enough for text + data + bss.
4. Read the reloc table, fixup table, export table, text, and data into the block.
5. Apply internal relocs: add the runtime base to each recorded offset.
6. Resolve external fixups through the kernel symbol table. For `CALL32`, allocate trampolines after the image data and patch the call site to point to the trampoline.
7. Zero the bss region.
8. Return a handle that records the base address and export table.

Because kernel heap pages are mapped executable (the kernel heap does not use the NX bit), the loaded image is directly executable.

## Kernel Symbol Table

The loader resolves external references through a manually maintained table `g_kern_syms[]` in `src/kernel/udll.c`. Current exports include window-manager functions (`wm_create_dialog`, `wm_destroy_window`, `wm_window_add_widget`, `wm_window_anchor`, ...), UI widget functions (`ui_button_init`, `ui_textinput_init`, `ui_dropdown_init`, `ui_dropdown_add`, ...), graphics primitives (`gfx_fill`, `gfx_text`, `gfx_rect`, `gfx_text_width`, `gfx_fill_blend`), VFS functions (`vfs_list`, `vfs_read`, `vfs_write`, `vfs_stat`), memory/string utilities, and `sched_ticks`.

When a UDLL needs a new kernel function, add the `{name, address}` pair to `g_kern_syms[]`.

## File Dialog UDLL

`src/udll/filedlg/filedlg.c` exports one function:

```c
typedef void (*FileDialogCallback)(int result, const char *path, int encoding, void *ctx);

void file_dialog_show(int mode, const char *title, const char *initial_path,
                      const char *ok_text, const char *cancel_text,
                      FileDialogCallback cb, void *ctx);
```

- `mode` — `0` for Open, `1` for Save.
- `title` — window title.
- `initial_path` — directory to open. In Save mode, if the path ends with a filename, that filename is pre-filled.
- `ok_text` — label for the confirmation button (e.g., `"Open"`, `"Save"`, `"Load"`). If `NULL`, defaults to `"Open"` or `"Save"`.
- `cancel_text` — label for the cancel/close button. If `NULL`, defaults to `"Cancel"`.
- `cb` — callback invoked when the dialog closes.
- `ctx` — opaque user context passed to the callback.

The callback receives:

- `result` — `1` if the user confirmed, `0` if cancelled.
- `path` — the selected file path, or `NULL` if cancelled.
- `encoding` — selected encoding index in Save mode (`0=UTF-8`, `1=ASCII`, `2=UTF-16`), or `-1` in Open mode.

### Layout

The dialog is a fixed 520x360/400/420 window. Widget coordinates are computed relative to the window content area (`content_height = window_height - WM_TITLE_H - 1`). This guarantees buttons and the encoding dropdown stay inside the content area regardless of the title bar height.

Save mode includes:

- file list (top area)
- filename text input (bottom left)
- encoding dropdown (bottom right)
- OK and Cancel buttons (bottom right)

Open mode includes only the file list and the OK/Cancel buttons.

### Usage Example (Notepad)

```c
static struct UdllHandle *g_filedlg;
typedef void (*fdlg_show_t)(int mode, const char *title, const char *initial_path,
                            const char *ok_text, const char *cancel_text,
                            void (*cb)(int, const char *, int, void *), void *ctx);
static fdlg_show_t g_filedlg_show;

static void ensure_filedlg(void)
{
    if (!g_filedlg)
    {
        g_filedlg = udll_load("/lib/filedlg.udll");
        if (g_filedlg)
            g_filedlg_show = (fdlg_show_t)udll_get_proc(g_filedlg, "file_dialog_show");
    }
}

static void on_save_result(int result, const char *path, int encoding, void *ctx)
{
    (void)encoding; (void)ctx;
    if (result && path)
        vfs_write(path, g_text, g_text_len);
}

static void show_save(void)
{
    ensure_filedlg();
    if (g_filedlg_show)
        g_filedlg_show(1, "Save File", "/var/documents/text.txt",
                       "Save", "Cancel", on_save_result, 0);
}
```

## Security and Limitations

- UDLLs run in kernel space. A buggy or malicious UDLL can crash the system. Only load UDLLs from trusted paths (`/lib/`).
- The symbol table is fixed at compile time. There is no runtime symbol discovery.
- Export/fixup names are limited to 31 characters plus null.
- The current format has no code signing or versioning beyond the single `version` field.
- UDLLs are loaded into kmalloc memory and are not paged or swapped.

## Future Work

- Add a UDLL dependency field so a UDLL can request other UDLLs.
- Extend the symbol table automatically from a linker-generated map instead of a hand-written list.
- Add a ring3 syscall-based equivalent for user applications that do not need direct kernel object access.
